# Security Notes

## Baseline Controls
- `SECRET_KEY` is required at startup.
- Credentials are delivered as file-backed Docker secrets, not environment
  variables in `docker-compose.yml` (see "Secret Handling" below).
- Default API permissions are authenticated.
- Write operations on documents are restricted to editor/admin roles.
- CORS defaults to explicit allowlists (`CORS_ALLOWED_ORIGINS`).
- CSRF and session cookie security defaults to secure in non-debug mode.
- DRF throttling enabled (`anon`, `user`, plus scoped throttles such as `upload` and `search`).
- File upload validation enforces extension and size caps.

## Required Runtime Inputs
- `SECRET_KEY` (secret: `django_secret_key`)
- `POSTGRES_PASSWORD` (secret: `postgres_password`)
- `POSTGRES_DB` (plain env)
- `POSTGRES_USER` (plain env)

## Secret Handling
Every credential is a file-backed Docker secret declared in the top-level
`secrets:` block of `docker-compose.yml` and sourced from `./secrets/*.txt`
(gitignored). Compose mounts each one read-only at `/run/secrets/<name>` and
only into the services that declare it, so the database password is not
present in the `frontend` or `caddy` containers at all.

Services receive `<VAR>_FILE=/run/secrets/<name>` rather than `<VAR>`:
- `postgres` and `minio` implement the `*_FILE` convention themselves.
- `backend`, `celery_worker`, and `agent` expand it via
  `backend/ilm_shamela/env_secrets.py`, called at the top of Django settings.
- `backend/load_secrets.sh` does the same for the shell steps in
  `entrypoint.sh` that run before Python starts (the `pg_isready` wait).

What this does and does not buy you:
- Secret values no longer appear in `docker inspect`, `docker compose config`,
  or the service definitions in version control.
- Values *are* still present in the environment of the Python process that
  needs them, because the loader materialises them into `os.environ` — roughly
  a dozen modules read these keys with bare `os.environ.get`. Anyone who can
  execute code inside the `backend` container can still read them.
- The files on the host are the sensitive artifact. Keep `./secrets` at mode
  `0600` and off backups that leave the host.

## Role Model
- Reader: authenticated read access.
- Editor/Admin: upload/update/delete access.
- Admin/staff: metrics endpoint access.

## Recommended Production Hardening
- Rotate `secrets/django_secret_key.txt` from a secret manager rather than
  keeping the value generated by `scripts/init-secrets.sh`.
- Set strict `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and `CORS_ALLOWED_ORIGINS`.
- Enable HTTPS redirect and HSTS in production (`SECURE_SSL_REDIRECT=true`).
- Restrict `/api/metrics/` by network policy in addition to auth.
